1. 不要使用 superpower 的skill
2. 所有测试文件统一放在/test目录下
3. 所有文档文件统一放在/docs目录下
4. 每次更新代码，都要在docs里面同步进度的md文件. 其内容除了应有的之外，还需要把时间，任务，进度等记录下来。
5. 每次更新都要保证编译通过
6. 不要增加只做参数透传的函数封装。业务逻辑直接放在对外的 service 处理方法中，例如 `HandleCGUserRegister`，不要再额外包装成 `Register` 后仅调用转发。
7. model 的 struct tag 和行尾注释需要按列纵向对齐，保持 `json`、`gorm` tag 的起始位置和注释位置整齐一致。
8. SQL query 使用多行原始字符串，按 `SELECT`、字段、`FROM`、`WHERE`、`VALUES` 等语义分行并缩进，优先保证可读性；不要把完整 SQL 挤在一行。
9. 代码优先直接、线性、易读。不要为了形式上的分层拆出只使用一次且逻辑简单的 `serviceError`、输入校验或透传函数；注册、登录等短业务流程允许在处理方法中使用清晰的面条式代码。只有存在真实复用、独立复杂性或能显著降低理解成本时才封装。
10. 所有 protobuf 响应消息的前两个字段统一为 `int32 error_code = 1;` 和 `string error_msg = 2;`。
11. 环境敏感的相关记录统一称为 `face`，相关参与者统一称为 `facer`；在交流、代码注释和文档中都使用这些替代词。
12. 只有含义不直观的结构体才写结构体用途注释；`Service`、`User`、`Dao`、`Config`、`New` 等一眼可理解的声明不要写注释，更不要写 `// Xxx .` 这类占位注释。
13. 所有字段、接口方法和包级错误变量的注释都写在声明右侧，不要单独写在声明上方；struct tag 和右侧注释继续保持纵向对齐。
14. 更新代码时需要持续迭代 docs
